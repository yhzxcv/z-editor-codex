# 数据文件格式

一个 `data/ch-<id>.js` 就是一章。**这些文件是网站的唯一数据来源，之后手工维护，
不再依赖 `代码图鉴.txt`。** 增删改条目直接编辑这里即可，改完刷新页面就生效，没有构建步骤。

## 一个文件长什么样

```js
Codex.add({
  id: 'zombie',                  // 唯一标识，js/chapters.js 里靠文件名引用
  title: '僵尸代码',              // 章节 chips 上显示的名字
  rtid: 'ZombieTypes',           // 可选，复制格式选「RTID语句」时用的表名后缀
  intro: [ '……' ],               // 可选，章节前言
  groups: [
    // 形态一：普通分组，直接挂条目
    { title: '神秘埃及',
      note: '可选，分组说明',      // 显示在分组标题右边的小字
      items: [
        { name: '木乃伊僵尸', code: 'mummy' },
        { name: '无尽埃及巨人僵尸', code: 'egypt_gargantuar_danger' },
      ] },

    // 形态二：大类，挂子分组（植物用的就是这种，两级）
    { title: '图鉴中的植物',
      note: '可选，大类说明',
      children: [
        { title: '神秘埃及', items: [ /* … */ ] },
      ] },
  ],
});
```

`items` 和 `children` **二选一**。混用的话 `children` 优先，同时挂的 `items` 会被当成一个同名分组处理。

## 章节字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 唯一标识，设置和 `js/chapters.js` 都引用它，**别改** |
| `title` | 是 | 章节 chips 上显示的名字 |
| `rtid` | 否 | RTID 表名后缀，见下 |
| `intro` | 否 | 章节前言，显示在章节标题下面 |

`rtid` 只影响「复制格式 → RTID语句」这一档：选中时复制的内容是
`"RTID(<code>@<rtid>)"`（**连外层引号一起**，因为关卡 JSON 里的值就是这个形状），
比如植物章声明 `rtid: 'PlantTypes'`，点豌豆射手复制出来就是
`"RTID(peashooter@PlantTypes)"`。

**不支持 RTID 的内容不写这个字段就行，复制时会回退成带引号**
（`"peashooter"`，不是裸代码）——勾了 RTID 的人要的是能直接粘进关卡 JSON 的
字符串字面量，那个语境下裸代码一样是错的。后面几章（音乐、主题、模块 JSON 之类）
没有 RTID 表，就属于这种情况。

条目可以单独覆盖章节的设定：

| 条目写法 | 效果 |
|---|---|
| 不写 `rtid` | 跟随章节 |
| `rtid: ''` | 这一条明确不支持，回退带引号（章节有表名也盖掉） |
| `rtid: 'XxxTypes'` | 这一条改用别的表名 |

**「不写」和「写空串」是两件事**，`js/codex.js` 的 `normItem` 分得开，别把条目级
`rtid: ''` 当成没写。

**表名写错不会报错、只会静默复制出错的东西**，所以 `tools/check.js` 里有一道白名单
校验（`RTID_TABLES`），章节级和条目级都拦。新增章节要支持这一档时，先把表名加进那个
数组。白名单放在自检工具而不是 UI 里，是为了不让界面耦合具体表名。

## 条目字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 中文名，列表主行，也是搜索和拼音首字母的数据源 |
| `code` | 是 | 游戏代码。**点击整行复制的就是它**，必须匹配 `[A-Za-z][A-Za-z0-9_]*` |
| `src` | 否 | 来源小字，灰色标签。原 TXT 里 `[方括号]` 或降级的父级标签会落到这里 |
| `note` | 否 | 备注小字，橙色标签。原 TXT 里 `（括号）` 的内容 |
| `rtid` | 否 | 单独指定或关掉这一条的 RTID 表名，见「章节字段」那节 |

`name` 里含中文引号（如 `“哈姆雷特”僵尸`）没问题。字段值里的单引号需要写成 `\'`。

## 分组字段

| 字段 | 说明 |
|---|---|
| `title` | 分组标题，也是分组 chips 和侧栏目录上显示的文字 |
| `note` | 可选，分组说明小字 |
| `items` / `children` | 二选一，见上 |

分组标题留空字符串也可以（会被当成无标题分组），但没必要。

## 加内容

**加条目**：找到对应分组，往 `items` 里加一行。代码里有下划线会更好搜（去下划线的写法也能命中）。

**加分组**：往 `groups` 里加一项。顺序即页面上的显示顺序。

**加章节**：新建 `data/ch-xxx.js`，然后在 `js/chapters.js` 的 `CODEX_MANIFEST` 数组里加一行路径。
数组顺序就是章节 chips 的顺序。如果这一章的代码也按 `RTID(code@表名)` 复制，还要在文件里声明
`rtid`，并把表名加进 `tools/check.js` 的白名单。

**从 TXT 批量导入**：`tools/migrate.py` 是当初把 `代码图鉴.txt` 一次性导成数据文件的工具。
**本仓库只放网站，所以它和 TXT 源文件都不在这里**，留在编辑器仓库 Z-Editor 里
（工具最后的版本在 Z-Editor 的 `1bfc78f` 提交，路径 `codex-site/tools/migrate.py`）。

其余 7 章还要用它，实际流程是：**在 Z-Editor 那份检出里跑**（TXT 就在那儿，工具按「`codex-site`
的上一级」找 TXT 的路径假设在那里也成立），生成 `data/ch-*.js` 之后再把文件拷进本仓库。

工具**默认不覆盖已存在的文件**——这些数据文件是手工维护的唯一真源，误跑一次
（不给参数＝处理全部章节）会把手工改动整个冲掉。植物和僵尸两章尤其不能再跑迁移。

`代码图鉴.txt` 的格式很随意，解析规则只会越来越复杂，所以新内容更推荐直接编辑数据文件。

## 改完自检

```bash
node tools/check.js
```

会检查：字段完整性、代码格式、有无空分组、序号唯一性，以及一批检索用例
（中文名 / 代码片段 / 去下划线 / 拼音首字母 / 跨章节 / 多关键词）。
改动数据结构之后跑一下，比在浏览器里肉眼翻要快。

## 不要动的东西

- **`id`**：`js/chapters.js` 和浏览器本地设置都引用它。
- **条目顺序**：搜索结果的同分排序会用到原序，顺序变了结果顺序也会变。
- `code` 字段只是个字符串，改它不影响游戏本身，但用户复制的就是它，改错等于害人。
